# MTG Dashboard — State of the Project Review

## What this is
Personal SQLite + Streamlit dashboard replacing an Excel/Office 365-based MTG collection and deck tracker. Tracks a personal card collection, 20+ Commander decks, maybeboards, game history, and analytical views. Playgroup includes Joe G, Anthony, and Joe M, whose decks appear in game logs but aren't fully tracked in the system.

## Status: fully built and tested (within sandbox constraints — see caveat at bottom)

Migration/data-layer foundation is complete and validated. The Streamlit dashboard is built out across **5 pages**, all backed by a shared library, all writable directly (no CSV editing required for day-to-day use anymore).

**Phase 1 refactor applied:** the Retired Decks concept (`is_active`/`successor_deck_id`) was removed entirely — every tracked deck is now assumed active. The standalone Tag Editor page was folded into the Editor page as a new "Card Tags" tab, and the separate "Deck Tags" feature (the `deck_tags` table) was removed outright — deck-level notes live in the description/combos/tutors fields instead. The Editor's Card Data "Refresh" action now also automatically prunes the collection (see below). Databases built before this change keep their old `is_active`/`successor_deck_id`/`deck_tags` columns physically in place (nothing is destructively dropped from a live SQLite file); `ensure_schema()` just normalizes the data (every deck → active, no successor) on connect, and the app code no longer reads or writes any of it.

**Phase 2 (Editor/Collection enhancements + new Commander Game Tracker) applied:** Date Acquired now uses a real calendar date picker (defaults to today when adding a lot). Deck Themes moved from free text to a dropdown backed by a master `theme_catalog` table you manage directly (add/remove entries in an Editor expander); removing an entry only changes what the dropdown offers, never touches a deck's existing assignments. Game Changers got the same treatment on the category side (`game_changer_category_catalog`) plus a brand-new Editor tab showing every Game Changer card (Scryfall-flagged or custom-tagged) with art, editable categories, owned quantity, and how many decks currently run it. Collection got Showcase/Borderless filter+columns (`cards.is_showcase`/`is_borderless`, populated from Scryfall's `frame_effects`/`border_color` at fetch and refresh time, with an MDFC front-face fallback). Decks got an optional custom cover-image thumbnail (`decks.cover_image_path`, a user-uploaded PNG saved under `image_cache/deck_covers/`), the Image Grid default bumped from 24 to 48 cards/page, an editable Win Conditions/Strengths/Weaknesses section in Deck Info (these tables already existed in the schema but had no write path before), and Top 10 Most Expensive / Top 10 Saltiest card panels. Salt scores (`cards.edhrec_salt`) are a new hand-maintained field — Scryfall's API doesn't expose EDHREC salt, so this is edited directly in the Editor's Card Data tab and deliberately never touched by the Scryfall refresh action. Finally, a whole new **Commander Game Tracking** page: log a game (up to 4 seats, each a tracked deck via dropdown or free text for an opponent, with an optional player name and win flag per seat, plus notes), an actual rendered game history (not a raw table) with a way to delete a mis-entered log, and win-rate comparisons by deck (existing `deck_stats` view) and by player (new `player_stats` view, `game_participants.player_name` column — only populated for games logged from now on).

**Phase 3 (Mana Curve & Color Breakdown, MDFC awareness, Weighted Mana Graph, Commander Cast Probability, Mana Text Rule Parser) applied:** Cards with a Land face on EITHER side of a Modal Double-Faced Card (e.g. `type_line` "Instant // Land") are now recognized as lands everywhere it matters — mana-curve exclusion, the Land Probability page's land count, and every color-source calculation — via a new MDFC-aware `is_land` column (`formatting.has_land_face()`, wired into `card_view.add_derived_columns()`), replacing the old front-face-only `card_type == "Land"` check used for these specific purposes (the existing `card_type` bucket itself is unchanged, still front-face-only, still used for display elsewhere). Decks & Maybeboard's Mana Curve chart is now non-land-card-only (MDFC-aware) and stacked/itemized by either Card Color or Card Type (a toggle), built directly from the already-loaded deck dataframe rather than a flat SQL count — the old `queries.deck_mana_curve()`/`loaders.load_deck_mana_curve()` are left in place (additive policy) but no longer called from the page. A new keyword/text rule parser (`formatting.classify_mana_colors()`) reads a card's own oracle text to classify what it can produce — "any color" phrasing (Command Tower, City of Brass, Exotic Orchard, Birds of Paradise, ...) is flagged as an Any-Color source even though those cards' own `color_identity` field is empty (no colored symbols in their text), a bare `{C}` with nothing else (Access Tunnel) is Colorless, plain colored symbols set specific colors, and anything unparseable falls back to the `color_identity` field. `formatting.is_mana_rock_or_dork()` uses the same text parsing to flag nonland Artifacts/Creatures with a mana ability. The Land Probability page's existing color-source counting (`probability.count_color_sources()`) now uses this parser instead of trusting `color_identity` alone, fixing the any-color-land gap in both the lands-only and "include nonland" modes. Two new engines were added to that page: a **weighted mana-source availability graph** (`probability.mana_source_category_counts()` + `weighted_mana_expectation()`) — turn-by-turn EXPECTED count (not "at least one" probability) of sources in each of Rocks/Dorks, Colorless, Any Color, and each WUBRG color, via hypergeometric linearity of expectation — and a **Commander Cast Probability engine** (`probability.parse_colored_pips()` + `commander_cast_probability_by_turn()`), Turn 1–10, compounding the land-drop probability (enough lands drawn for the commander's mana value) with the color-source probability (enough sources of each colored pip in its cost) as independent factors; looks up the commander/partner's own card row via a new `queries.cards_by_name()` since the commander lives in the command zone, not the shuffled library. Hybrid/Phyrexian pips (`{U/B}`, `{U/P}`) are deliberately excluded from the color requirement rather than counted toward every color they mention, since they can be paid another way. The "Check a specific card" tool now excludes pure lands (`formatting.is_pure_land()` — a card whose type line is Land on every face) per spec, while still listing land-having MDFCs since their other face is a real card to check for. **No schema/migration changes were needed** — `cards.oracle_text` already existed and was already populated by the Scryfall fetch path; Phase 3 is Python-logic-only.

**Phase 4 (UI/nav restructure + table fixes, Prompt Pass 4) applied:** The home page (`dashboard.py`) is now a landing page of image-backed deck tiles (`card_view.render_deck_landing_grid()` + `queries.list_decks_with_covers()`) — cover image if the deck has one, else the commander's own card art (resolved from that deck's own `deck_cards`/`cards` rows, not a bare global name lookup), else a placeholder; clicking a tile navigates (plain `<a href>`, same tab) to `Decks?deck_id=<id>`, and that page reads/consumes the query param via `st.query_params` to pre-select the deck (pre-seeding `st.session_state["deckpage_deck_select"]` before the selectbox is created, then `del`-ing the param so it doesn't keep re-forcing that deck back in on a later rerun after the user picks something else). The **"Decks & Maybeboard" page/file was renamed to "Decks"** (`pages/2_Decks_and_Maybeboard.py` → `pages/2_Decks.py`) — it still covers the maybeboard via the existing Board toggle, only the section name/URL changed; every in-app/docstring/README reference to the old name was updated to match. Within that page, the Optimized Mana / Game Changers / Reserved List row was moved to sit directly under Win Conditions/Strengths/Weaknesses (ahead of Themes/Mana Curve, which used to come first). Three table tweaks: the Game Changers table no longer shows the `scryfall_flag` column (every row there is already Game-Changer-flagged or custom-tagged, so it only ever rendered a static "1"); the Reserved List table shows each card's current price instead of quantity run (`queries.deck_reserved_list_cards()` now selects `current_price_usd` instead of `dc.quantity`); the Top 10 Most Expensive table hides quantity (unit pricing only) and adds a Purchase Price / Cost Paid column sourced from `collection.price_paid`, summed across whatever lot(s) have `location` matching the deck's name (`queries.deck_price_top10()`). The Mana Curve chart's "stack by Color" mode now always groups/orders as W, U, B, R, G, Multi-color, Colorless (`formatting.mana_curve_color_bucket()` collapsing any multi-color `color_display` combo into one "Multi-color" bucket, `formatting.MANA_CURVE_COLOR_ORDER`) instead of an alphabetical-with-Colorless-last fallback, with a fixed hex color per bucket (`formatting.MANA_CURVE_COLOR_HEX`) passed to `st.bar_chart(..., color=[...])`; the "stack by Type" mode is unchanged. The sidebar's "🔄 Refresh data" button now also resets every active sidebar filter back to its default on click (`card_view.register_filter_key()`/`reset_filters()` — every filter widget `render_filter_panel()` builds registers its own session_state key into a per-session set; a page can register a bespoke filter control the same way, which the Collection page's new deck-status toggle does) — clearing session_state for a widget's key must happen before that widget is re-instantiated on the next run, which is exactly what happens here since the reset runs inside the button's own click handler, right before `st.rerun()`. The Collection page got a new "Deck status" sidebar toggle — All / In a deck / Not in a deck / Not in a deck OR another location — backed by a new `in_deck` column on `queries.collection_dataframe()` (1 if that printing's `scryfall_id` is used in any deck's mainboard via `deck_cards`, the same test `writes.prune_collection()` already uses); "Not in a deck OR another location" was implemented as the narrower AND reading (not in any deck's mainboard AND `location` is blank/NULL, i.e. truly unassigned on both fronts) rather than the broader OR reading, since that's the bucket most useful for spotting cards with no home at all — **this interpretation was an assumption, not confirmed with the user, and is worth revisiting if it doesn't match what they meant.** The sidebar filter facets (`single_facets` in `render_filter_panel()`) were already `st.multiselect`-based (multi-selection already worked) going into this pass, so no change was needed there. **No schema/migration changes were needed** — Phase 4 is Python/query-logic and page-layout only.

**Post-Phase-6 hotfix — pandas NaN crash in image resolution:** Reported after Phase 6 delivery: opening the dashboard's home page threw `TypeError: join() argument must be str, bytes, or os.PathLike object, not 'float'` from `formatting.resolve_local_image()`. Root cause: when a column loaded via `pandas.read_sql_query()` is NULL for every row in the reporter's pandas/environment (e.g. no deck has a custom cover image yet), pandas types that column as `float64` and represents each missing value as `NaN` — a `float`, not `None`. `bool(float('nan'))` is `True` in Python, so the old `if not local_image_path:` guard didn't catch it, and the NaN reached `os.path.join()`. This predates Phase 6 (the affected code is Phase 4's `render_deck_landing_grid()`/`list_decks_with_covers()`) — Phase 4's own testing didn't catch it because the test data used at the time always had at least one non-NULL value in the affected column, keeping it `object`-typed with real `None`s instead of `NaN`; this specific type-inference quirk turned out to be pandas-version-dependent (not reproducible against this sandbox's pandas 3.0.2 with the same query, but confirmed via the reporter's real traceback). Fixed by tightening `formatting.resolve_local_image()` to require an actual non-blank `str` (rejecting `NaN`/`None`/any other type) rather than relying on truthiness, and applying the same fix defensively to `formatting.scryfall_card_url()` (same class of bug — not currently crashing, since it falls through to a harmless bogus URL string rather than a `TypeError`, but the same non-`str` values could reach it the same way). Every caller of `resolve_local_image()` (`card_view.py`'s three call sites, `pages/2_Decks.py`, `pages/4_Editor.py`'s two call sites) is fixed by this one change, since they all route through it. Validated by a new `scripts/_test_hotfix_nan_image_offline.py` — direct unit checks (`NaN`/`None`/empty-string/whitespace/wrong-type inputs to both functions), and, since the exact pandas-version type-inference quirk didn't reproduce via a real query in this sandbox, a hand-built DataFrame carrying the exact failure signature (an all-`NaN` `float64` `cover_image_path` column) run through the REAL `card_view.render_deck_landing_grid()`/`_deck_image_src()` call path — the same one that crashed — confirming it now completes without raising. Full regression re-run (Phase 4, Phase 5, Phase 6, migration) confirmed nothing else broke.

**Post-Phase-6 UX tweak — `run.py` launcher menu reordered, migration de-fanged:** Requested after using the dashboard for a while: the launcher's numbered menu put "Run/refresh database migration" as option 1, front and center — a real risk since `migrate.py` is fully destructive (its own docstring: a re-run "deletes and rebuilds mtg_collection.db from scratch" and "will silently discard any dashboard-made edits since the last migration"), so an accidental keypress there could wipe out everything entered through the Editor since the last migration. Reworked so the numbered menu (1–6) now only lists the safe, everyday actions — **Launch dashboard is option 1** (the actual common case), followed by both Moxfield exports (deck, and the Phase 6 collection CSV — `run.py` had never been updated to expose the new `export_moxfield_collection.py` CLI script until now, a gap from Phase 6 itself), image sync, and card-data refresh. The migration is no longer a numbered option at all — it's invoked by typing the word `migrate` (case-insensitive) instead of a digit, listed separately under a "Rarely needed" heading with its risk spelled out inline, and now requires typing `REBUILD` (exact, case-sensitive) at a confirmation prompt describing exactly what it will destroy before it actually runs anything — mirroring the Editor's own "type the exact deck name to confirm deletion" precedent for irreversible actions. First-time setup (no `mtg_collection.db` yet) still works: the "no database found" message and every gated option's tag now point at typing `migrate` instead of a numbered option. Validated with a mocked-`input`/mocked-`subprocess.run` harness (not a separate test file — a one-off validation script, since `run.py` is a thin CLI launcher with no existing test-file convention of its own): confirmed cancelling at the `REBUILD` prompt never invokes `migrate.py`, confirmed it only runs on an exact match, confirmed every numbered option is still correctly gated behind DB existence, confirmed the new collection-CSV export option builds its subprocess args correctly (`--not-in-deck` / `-o` flags), confirmed option 1 launches the dashboard once a DB exists, and confirmed a stray/garbage menu entry never triggers migration.

**Phase 6 (Collection auto-complete, Deck Building Auto-Add, Moxfield Collection CSV export, Prompt Pass 6) applied:** Three features landed, all scoped to collection management and Moxfield export — no changes to probability/mana-curve logic this pass. (1) **Collection auto-complete + printing selector** — the Editor's Collection tab "Add a card" form now offers a type-ahead suggestion list (`queries.search_card_names()`, prefix matches ranked ahead of contains-only matches) drawn from the local `cards` table itself (this project's own "master card registry" — no network needed), refreshing once the text input commits (Streamlit has no true per-keystroke rerun without a custom component, so "as you finish typing or press Enter" is the honest, accurate description used in the UI caption rather than overselling live JS autocomplete). Picking a suggestion (or leaving it on "use exactly what I typed") then surfaces a second selectbox, `queries.card_printings_by_name()`, listing every printing of that name already known locally (set + collector number + current price) — selecting one uses that exact `scryfall_id` directly, bypassing the name/set/number resolution path entirely. A "🔍 Check Scryfall for other printings" button (shown only when `card_resolver.scryfall_available()`, i.e. `requests` is installed) calls a new `scryfall_lookup.ScryfallClient.get_all_printings()` (Scryfall's `/cards/search` with `unique=prints`) via `card_resolver.fetch_additional_printings()`, which inserts any printing not already local (`INSERT OR IGNORE`, existing rows never touched) so the printing selector can offer them too — this is the one place in the dashboard that deliberately fetches more than "whatever's actually referenced" (see `scripts/scryfall_lookup.py`'s own docstring), but it's an explicit, single-card, user-initiated action, not a background bulk sync. The manual Set Code / Collector Number fields are still there as a fallback for a genuinely new card with zero local printings (unchanged live-Scryfall-lookup behavior via `resolve_or_fetch_card()`). (2) **Deck Building Auto-Add** — `writes.auto_add_to_collection()` (paired with a `writes.collection_has_card()` presence check) is now called right after a successful "Add to mainboard" in the Editor: if the printing being added has NO collection lot at all yet (by exact `scryfall_id`, not by card name — a different printing of the same card still gets its own starter lot), a starter lot is created automatically — quantity matching what was just added to the deck, `location` defaulted to the deck's own name (the same "sleeved in this deck" free-text convention `collection.location` already uses everywhere else), no foil, dated today, `source` tagged `"Auto-added (deck build)"` so these are easy to spot/audit later. This keeps the collection from silently drifting out of sync with what decks actually run, matching the project's "dashboard is the source of truth" philosophy applied to deck building specifically. **Deliberately NOT wired into the Maybeboard add flow** — a maybeboard card is explicitly "under consideration," not a committed deck inclusion, so auto-adding it to the collection would overstate ownership; this was a judgment call (not confirmed with the user) worth revisiting if it doesn't match the intent. (3) **Moxfield Collection CSV exporter** — `dashboard_lib/moxfield_export.py` gained `collection_export_rows()` / `collection_csv_row()` / `export_collection_csv_text()`, generating one CSV row per **printing + foil status** owned (collection lots for the same printing/foil are intentionally kept as separate rows elsewhere in the schema for price/date history, but Moxfield's own CSV format wants one row per printing/foil, not one row per lot — quantity and purchase price are SUMmed across whatever lot(s) match). Untracked bulk lots (`collection.quantity IS NULL`) are excluded, consistent with how "tracked" totals are already treated elsewhere in the app. Column mapping follows the prompt spec exactly (verified header-for-header against `moxfield_samples/moxfield_collection.csv`): Count = summed quantity; Tradelist Count = 0 whenever that exact printing is used in ANY deck's mainboard (reusing the same `EXISTS (... deck_cards ...)` test `collection_dataframe()`/`prune_collection()` already use), else equal to Count; Edition = lowercased set code; Condition/Language are constants ("Near Mint"/"English"); Foil = lowercase `"foil"` or blank; Tags is always blank (no in-dashboard concept maps to it); Last Modified defaults to the current timestamp (the schema has no real per-lot last-modified column to pull a historical value from — the prompt spec's own documented fallback); Alter/Proxy are always `"FALSE"` (no Proxy convention exists yet — see "Known open items"). Two export subsets are supported end-to-end: **Full Collection** and **Owned NOT in a deck** (`only_not_in_deck=True` filters to printings with zero deck usage at all). **Phase 5 (Land Probability calculation refinements + EDHREC Salt Score retirement, Prompt Pass 5) applied:** Three fixes/additions landed on the Land Probability page's calculation layer, plus one feature was retired dashboard-wide. (1) **"Check a specific card" (Section E)** used to show the same plain draw-probability curve for every card, since every mainboard card in a singleton Commander deck has the same quantity — it didn't actually use the card's own mana cost at all. It now calls a new `probability.card_cast_probability_by_turn()`, which compounds THREE independent factors turn-by-turn (Turn 0/opening hand through Turn 8, per spec): drawing the card itself (its own quantity), drawing enough lands for its mana value, and drawing enough sources of each of its colored pips (reusing `count_color_sources()` at land-only granularity, same basis Section D already uses) — same "treated as independent, so an optimistic estimate" caveat already established for the Section D commander engine. A factor-breakdown expander (Drawn / Land factor / Color factor / Combined) mirrors Section D's existing UI pattern. (2) **Expected Land Drops** — the land-drop table (Section A) gained an "Expected lands seen" column: the probability-weighted EXPECTED total land count by each turn (linearity of expectation, same math family as the Phase 3 weighted mana-source graph), alongside the existing "at least N lands" probability column — a new `probability.expected_count_by_turn()` helper powers this, and `weighted_mana_expectation()` was refactored to call it per-category rather than duplicating the formula. (3) **Color availability bug fix** — `probability.count_color_sources(..., lands_only=False)` used to classify EVERY nonland card in the library, not just actual mana sources; `classify_mana_colors()`'s color_identity fallback (its last resort, for text the regex parser can't read) would then misidentify a plain nonland card sharing a color — e.g. a vanilla red creature with no mana ability at all — as an "R mana source" purely because its color identity happened to be R. The nonland side of the pool is now gated by `formatting.is_mana_rock_or_dork()` (the same flag `mana_source_category_counts()` already used), so only lands and verified mana rocks/dorks are ever classified — this affects both the Section B toggle ("also count nonland mana rocks/dorks") and, indirectly, anywhere else that calls `count_color_sources(lands_only=False)`. (4) **EDHREC Salt Score retired** — the prompt asked for a lightweight public API or a low-overhead MTGJSON lookup as fallbacks before accepting removal as a last resort; research found neither cleared that bar. EDHREC has no official public API for salt scores at all. MTGJSON does carry an `edhrecSaltiness` field (added in their v5.2.0 Card Data Model), but only inside their full-size exports (`AllPrintings`/`AllIdentifiers`/`AtomicCards`, each hundreds of MB+) — downloading and periodically re-syncing a dataset that size for one hand-sized float field is a poor fit for this personal-scale, mostly-offline tool, so the fail-safe branch was taken: the whole feature (Editor's "Salt Scores" sub-editor, the Decks page's "Top 10 Saltiest" panel, `queries.deck_salt_top10()`, `writes.set_card_salt_score()`/`bulk_set_salt_scores()`, `loaders.load_deck_salt_top10()`, and `edhrec_salt` from `CARD_COLUMNS`) was removed. Per this project's additive/non-destructive schema policy, `cards.edhrec_salt` itself was NOT dropped from `schema.sql` — any values a user hand-entered before this pass are physically preserved, the app just no longer reads, writes, or displays them anywhere. **No schema/migration changes were needed beyond that comment update** — Phase 5 is Python-logic and page-content only. Validated by a new offline harness, `scripts/_test_prompt_pass5_offline.py` (hand-built library dataframes for the color-source fix and the new card-cast-probability math — including a direct check that a 1-drop and a 6-drop singleton no longer produce identical curves — plus a scratch schema.sql-built database confirming `edhrec_salt` still physically exists on `cards` while no query, write, or loader function references it anymore), alongside a full re-run of the existing `_test_phase4_offline.py` and `_test_migrate_offline.py` suites to confirm nothing regressed.

**Phase 7 (Commander Game Tracking overhaul — edit, validation, autofill, tabs, ELO/head-to-head, Prompt Pass 7) applied:** A full pass over the Commander Game Tracking module, all five prompt-spec areas landed. (1) **Edit functionality** — `writes.update_game()` (date/note update + full delete-and-reinsert of `game_participants`, same whole-list-replace pattern as `set_deck_rank_list()`) backs a new "✏️ Edit a logged game" expander: pick a game, get a form pre-filled from `queries.game_detail()` (a new, deliberately uncached single-game lookup), edit, save. `create_game()`/`update_game()` were refactored to share `_insert_game_participants()` and a new `_validate_game_participants()` helper. (2) **"Game #" removed** — no numeric game identifier is shown anywhere; the Edit/Delete pickers now use `st.selectbox(..., format_func=...)` keyed on the real `game_id` (date + rendered participants as the label) instead of the old dict-keyed-by-label approach, which also fixed a real latent bug: two games with an identical label (same date, same participants) used to silently collapse to one dict entry, making the earlier one unreachable for deletion. Sort order (date, then `game_id` as a same-day tiebreaker) was already correct going in and didn't need to change. (3) **Autofill/dynamic dropdowns** — two new query functions, `queries.distinct_player_names()` and `queries.distinct_untracked_deck_names()` (the latter includes both always-free-text opponent decks AND any deck detached by a since-deleted tracked deck), feed a known-value dropdown for both the Player and Opponent's Deck fields on both forms, following the exact same "dropdown with a sentinel + always-visible free-text fallback, decide precedence after submit" pattern the Tracked Deck field already established — deliberately NOT Streamlit's newer `accept_new_options` combobox param, since the project's floor is `streamlit>=1.32` and that feature isn't guaranteed present. (4) **Tracked Deck Deletion audited** — `writes.delete_deck()`'s existing detach-not-delete behavior (`game_participants.deck_id` → NULL, `deck_name` text preserved) was confirmed already correct; the one real gap found was `is_own_deck` staying 1 on a detached row even though it no longer maps to a tracked deck, now fixed to clear to 0 alongside `deck_id` (a hygiene fix — `is_own_deck` isn't read by any query/page today, so this doesn't change any currently-visible behavior). ## Critical philosophy shift: migration is now one-way

`migrate.py` wipes and rebuilds `mtg_collection.db` from the CSVs **every time it runs**, with zero attempt to preserve anything edited in the dashboard since. This was explicitly requested — an earlier version had a complex tag-preservation backup/restore mechanism that was deliberately ripped out and simplified.

**The rule: run `migrate.py` once for initial CSV import, then never again.** All ongoing management (card tags, deck metadata, mainboard/maybeboard, themes, collection, Game Changer categories, salt scores, game log) happens in the dashboard from then on.

Because of this, schema changes can no longer ride in on a re-migration. `queries.ensure_schema()` (called automatically inside `get_connection()`) applies additive, non-destructive upgrades on every connect: `ALTER TABLE` for new columns, `CREATE TABLE`/`CREATE VIEW` for new tables/views. This is how `cards.is_reserved` reached existing databases in Phase 1, and how the Phase 2 additions (`is_showcase`/`is_borderless`/`edhrec_salt`/`cover_image_path`/`player_name`, plus the `theme_catalog`/`game_changer_category_catalog` tables and `player_stats` view) reached them too. **Important nuance caught during Phase 2 testing:** a brand-new install via `migrate.py` builds straight from `schema.sql`, so `theme_catalog`/`game_changer_category_catalog` already exist (empty) before `ensure_schema()` ever runs its "seed on first creation" logic — which only fires for *upgrading* a pre-Phase-2 database that doesn't have the table yet. `migrate.py` itself was updated to seed both catalogs directly (right after loading `deck_themes`/`game_changer_tags` from their CSVs), so fresh installs and upgraded databases both end up with a populated dropdown. Confirmed by re-running the project's own offline migration test against the real CSVs — 39 themes / 6 categories seeded correctly.

Auto-detects library size/land count excluding the commander, MDFC-aware.
4. **Editor** — deck rename (with optional `collection.location` cascade)/metadata/create/**delete** (cascades correctly, detaches rather than deletes historical `game_participants` rows, requires typing the exact name to confirm); a cover-image uploader and Win Conditions/Strengths/Weaknesses editor, both new in Phase 2; themes add/remove via a master-catalog dropdown (Phase 2); **Card Tags** (moved from the old standalone Tag Editor page) — bulk-edit any tag_type across a whole deck's mainboard in one table; mainboard add (with live Scryfall resolution for brand-new cards)/bulk-edit/remove — now also auto-adds a starter collection lot when the printing added isn't tracked in the collection at all yet (Phase 6, Deck Building Auto-Add); maybeboard add (same live Scryfall resolution, no auto-add)/bulk-edit/remove; collection add (real date picker, Phase 2; Phase 6 added a type-ahead name suggestion list plus a "choose the exact printing" second selector, with an optional live Scryfall lookup for printings not yet known locally)/bulk-edit/remove; **Game Changers tab** (new in Phase 2) — every Scryfall-flagged or custom-tagged card across the whole database with art, editable categories from a master catalog, owned quantity, and how many decks run it; **Card Data tab** — refreshes Reserved List/Game Changer/Showcase/Borderless/legality/price for every existing card by its permanent Scryfall ID with a progress bar, then automatically prunes the collection (see below) — the Salt Scores sub-editor that used to live at the bottom of this tab was removed in Phase 5 (see below).

"Log & manage games": log a game (up to 4 seats, each a tracked deck via dropdown, a known opponent deck, or free text, with autofill dropdowns for Player and Opponent's Deck sourced from prior entries as of Phase 7; submission blocked unless exactly one winner and every touched seat has a resolvable deck), rendered game history, and Edit (in place, Phase 7) / Delete expanders — no "Game #" is tracked or shown anywhere, entries sort by date then `game_id`. "Player & deck stats": win-rate comparisons by deck and by player (Phase 9: Win % cells shaded red-below/blue-above a 25% 4-player-pod baseline), plus (Phase 7) a multiplayer ELO rating per player (unshaded — no Win % column) and a head-to-head win-rate matrix (Phase 9: same red/blue shading).

## Data/schema facts worth remembering

- **`decks.color_identity` is concatenated letters** (`"RB"`), **not** comma-separated like `cards.color_identity` (`"B,R"`) — different parser needed for each (`fmt.deck_color_identity_letters` vs. `fmt.color_identity_display`). This was a real bug found and fixed mid-project.
- The commander card itself **is** a row in `deck_cards` (100 total = 99 + commander). Probability calculations subtract the commander/partner to get the true shuffled-library size. Phase 3's Commander Cast Probability engine looks the commander/partner's own card row back up by name (`queries.cards_by_name()`) since it needs their `mana_cost`/`cmc`, which the shuffled-library dataframe doesn't include (it's excluded from that dataframe on purpose).
- **MDFC land awareness (Phase 3):** `formatting.has_land_face(type_line)` checks BOTH faces of a card (split on `" // "`) for "Land" — this is distinct from `formatting.derive_card_type()`, which still only looks at the front face for display bucketing. `card_view.add_derived_columns()` adds this as a new `is_land` column used by the mana curve, Land Probability page, and color-source counting; the older `card_type == "Land"` check is still used elsewhere for display purposes where front-face bucketing is what's wanted.
- **Mana-source color classification (Phase 3):** `formatting.classify_mana_colors(type_line, oracle_text, color_identity)` is the keyword/text rule parser — "any color" phrasing in a card's own oracle text wins over its `color_identity` field (fixes Command Tower/City of Brass/Exotic Orchard, whose `color_identity` is empty), a bare `{C}` with nothing else is Colorless (Access Tunnel), plain colored symbols set specific colors, and `color_identity` is only the fallback for text this regex-based parser can't read. Hybrid/Phyrexian pips (`{U/B}`, `{U/P}`) in a mana COST (as opposed to a mana ability) are deliberately excluded from `probability.parse_colored_pips()`'s color-requirement count for the same "can be paid another way" reasoning. **Phase 5 fix:** `probability.count_color_sources(..., lands_only=False)` now gates its nonland pool through `formatting.is_mana_rock_or_dork()` before applying `classify_mana_colors()` — previously it ran the classifier over every nonland card in the library, and that classifier's `color_identity` fallback would misidentify plain same-colored nonland cards (no mana ability at all) as mana sources.
- **Per-card cast probability (Phase 5):** `probability.card_cast_probability_by_turn()` is the "Check a specific card" tool's engine — it's the commander-cast-probability approach (Phase 3) extended with a third independent factor (draw probability, using the card's own quantity in the shuffled library, since unlike a commander it isn't guaranteed to be available) on top of the existing land-count and color-source factors, turns 0 (opening hand) through 8. `probability.expected_count_by_turn()` is the single-category version of `weighted_mana_expectation()`'s (Phase 3) linearity-of-expectation math, pulled out as its own helper so the land-drop table's new "Expected lands seen" column can call it directly without building a category dict.
- `card_tags` is deck-scoped: PK is `(deck_id, scryfall_id, tag_id)`. There is no deck-level tags table anymore — that was removed in Phase 1.
- `cards.is_game_changer`, `cards.is_reserved`, `cards.is_showcase`, and `cards.is_borderless` are all pulled from Scryfall's live fields **at fetch time only** — they don't silently stay current. The Editor's Card Data tab / `refresh_card_data.py` is how you resync them later. `is_showcase` comes from `frame_effects` containing `"showcase"` (falls back to the front face's `frame_effects` for MDFCs, since the top-level list can be empty on those); `is_borderless` comes from `border_color == "borderless"`.
- **`cards.edhrec_salt` — feature retired in Phase 5, column kept.** EDHREC salt scores aren't exposed by the Scryfall API, and neither a lightweight public EDHREC API nor a low-overhead MTGJSON lookup turned out to exist (MTGJSON's `edhrecSaltiness` field only ships inside its full, hundreds-of-MB+ exports) — see the Phase 5 writeup above. The whole feature (Editor sub-editor, Decks page "Top 10 Saltiest" panel, and every supporting query/write/loader function) was removed, and `edhrec_salt` was dropped from `queries.CARD_COLUMNS`, so no dataframe in the app carries it anymore. The column itself is still physically declared in `schema.sql` (additive/non-destructive policy — nothing is ever dropped from a live database), so anyone's previously hand-entered values are preserved; there's just no read or write path to them left in the dashboard.
- `game_changer_tags` (custom sub-categories: Combo/Mana/Power/Stax-Unfun/Tutor/Value) is separate from `is_game_changer`. As of Phase 2 it has an in-dashboard editor (Editor → Game Changers tab), card-name-keyed (not deck-scoped) same as the table itself; the set of valid category names lives in a new `game_changer_category_catalog` table you manage separately (add/remove doesn't touch existing tag assignments). `mana_tags` remains CSV-only with no in-dashboard editor yet.
- **Theme dropdown (Phase 2):** `theme_catalog` is a new master list (`theme` TEXT PRIMARY KEY) that the Editor's Themes tab dropdown reads from — separate from `deck_themes` (the actual per-deck main/sub assignments, unchanged). Seeded once, either by `ensure_schema()` on an upgraded pre-Phase-2 database or by `migrate.py` on a fresh install, from whatever distinct theme names already exist in `deck_themes`.
- **Deck cover image (Phase 2):** `decks.cover_image_path` stores a path relative to `BASE_DIR`, same convention as `cards.local_image_path` — e.g. `image_cache/deck_covers/12.png`. Uploaded PNGs are written straight to that path from the Editor; no resizing/validation beyond the file-type filter.
- **Player names in game logs (Phase 2):** `game_participants.player_name` is new and nullable — historical rows imported by `migrate.py` from `games_played.csv` don't have one (the CSV baked player names into the opponent's deck-name string instead, e.g. `"Aesi, Tyrant of Gyre Strait (Anthony)"`, which is left as-is). Only games logged through the new Commander Game Tracking page populate this column, and the "win rate by player" view (`player_stats`) only reflects those.
- Deleting a deck clears its mainboard/maybeboard/card tags/themes/win-strengths-weaknesses, detaches (not deletes) its `game_participants` rows so other players' results in shared games survive (also clearing `is_own_deck` to 0 on those rows as of Phase 7 — see below), and optionally clears matching `collection.location` text.
- **Collection pruning** (`writes.prune_collection()`) runs automatically as part of the Card Data "Refresh" action: any collection lot with no assigned location, a quantity of 0/none, and not present in any deck's mainboard or maybeboard is deleted.
- Two deck names — Rakdos Showstopper and Vorevold, Sac Master — predate `deck_mapping.csv` and are registered directly in `migrate.py` (`FORMER_DECK_NAMES`) purely so their entries in `games_played.csv` link to a real `deck_id` rather than falling through to the free-text "unmatched opponent" path.
- **No "Game #" anywhere (Phase 7):** `games.game_id` is an internal primary key only — never surfaced to the user as a sequence to read meaning into. Game history, and the Edit/Delete pickers, are always ordered by `date` then `game_id` (same-day tiebreaker); the pickers show a date + participants label, never the id itself, though the id is still the underlying selectbox value so two games with an identical label stay independently selectable.
- **Game log autofill (Phase 7):** `queries.distinct_player_names()` / `distinct_untracked_deck_names()` source the Player / Opponent's Deck dropdowns from `game_participants` itself — `distinct_untracked_deck_names()` picks up both decks that were always free-text AND decks that used to be tracked but were later deleted (their `game_participants.deck_id` is NULL post-detach, same query condition either way).
- **Player ELO / head-to-head (Phase 7):** `queries.player_elo_ratings()` / `player_head_to_head_matrix()` are plain Python functions, not SQL views (ELO needs to process games in chronological order one at a time). Both are scoped to `player_name IS NOT NULL`, same as `player_stats`. ELO uses a multiplayer pairwise-decomposition variant (winner beats every other seat 1-0, non-winners draw 0.5-0.5 pairwise) with all of one game's deltas computed from a ratings snapshot at that game's start and applied together — NOT incrementally pair-by-pair, which would make results depend on player iteration order (a real bug this pass's test suite caught before it shipped). K-factor defaults to 20.

## Testing approach (important caveat)

No live Streamlit or network access exists in the build sandbox. Everything was validated via: a hand-built `streamlit` stub module simulating widgets/caching, an offline mocked-Scryfall migration harness for realistic test data, unit tests for every `dashboard_lib` write function against scratch SQLite databases, and full regressions after every change.

Phase 2 specifically added: a test that builds a synthetic pre-Phase-2-shaped database and runs `ensure_schema()` against it, confirming every new column/table/view appears, the two catalogs seed correctly from pre-existing `deck_themes`/`game_changer_tags` data, and a second `ensure_schema()` call is idempotent and doesn't clobber catalog edits made in between; direct unit tests for every new `writes.py`/`queries.py` function (theme/category catalog CRUD, game-changer tag assignment, salt scores, deck cover image, rank-list replace semantics, `create_game`/`delete_game`, the price/salt top-10 and win-rate queries); unit tests for `scryfall_lookup.to_card_row()`'s new Showcase/Borderless parsing (plain card, showcase-only, borderless-only, both, MDFC front-face fallback, and fields missing entirely); an end-to-end mocked `refresh_all_cards()` run confirming the new flags actually get written; and — importantly — a full re-run of the project's own real `_test_migrate_offline.py` harness against your actual CSVs (not synthetic data) to catch the fresh-install catalog-seeding gap described above before it shipped.

**None of this has been run against real Streamlit or real network access** — first actual use (launching the real dashboard, clicking through the new tabs and the new page, running a real Card Data refresh against live Scryfall) is the real-world validation still outstanding.

**Phase 6 testing specifically:** `queries.search_card_names()`/`card_printings_by_name()` were unit-tested against a hand-built scratch database (prefix-vs-contains ranking, case-insensitivity, blank-input and no-match edge cases), then re-run directly against the real shipped `mtg_collection.db` as a sanity pass (a "sol ring" search correctly surfaces just "Sol Ring", and its printing selector correctly lists all 6 real owned/known printings). `writes.auto_add_to_collection()`/`collection_has_card()` were unit-tested for first-add-creates-a-lot, second-call-is-a-no-op, and the "a different printing of the same-named card still gets its own lot" scoping rule, then exercised end-to-end against a scratch copy of the real database (added a real untracked card to a real deck, confirmed a starter lot was created with the deck's name as Location, confirmed calling it again was a no-op).
